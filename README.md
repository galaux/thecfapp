## Repository organisation

This Git repository is a monorepo that hosts two main parts:
- a GraphQL API (Clojure `deps.edn` project)
- a mobile app (Yarn project)

In order to meet Heroku's Build Packs requirement, this monorepo displays some
peculiarities in its file hierarchy:

```
.
├── docs/
├── api/
│   └── deps.edn
├── packages/
│   └── mobile/
│       └── package.json
├── bin/
│   └── build
├── app.json
├── README.md
├── package.json
├── project.clj
├── system.properties
├── Procfile
└── yarn.lock
```

- `./api/`: home of the Clojure `deps.edn` project for the API.
- `./project.clj`: an empty placeholder required to trigger the Heroku Clojure
  Build Pack installation.
- `./system.properties`: picked-up by Heroku to specify the JVM to install.
- `./bin/build`: a shell script overriding the Clojure Build Pack default
  behavior which would otherwise run Leiningen. This script assumes the mobile
  app is build and the resulting static assets are available in
  `./packages/mobile/build`.
- `./package.json`: a Yarn root configuration file to setup `./workspace/mobile`
  as a _Yarn package_. This setup is an artefact of the previous setup where
  this monorepo was Yarn only with four packages.
  TODO remove use of Yarn packages.
- `./packages/mobile/package.json`: the heart of the React mobile appliction.

## GraphQL domain classes and React Hooks

The API GraphQL schema is written by hand as EDN and lives in
`./api/resources/graphql/`.  The `mobile` queries and fragments
are also written by hand and live in:
- `./packages/mobile/src/graphql/`
- `./packages/mobile/src/**/*.graphql`

The Yarn script `codegen` declared in `./packages/mobile/package.json`
generates some `mobile` fragments and hooks based on
`./packages/mobile/graphql.schema.json` which in turns can be generated by

## Start the API without serving the mobile app

The API ships an in-memory [Datomic](https://www.datomic.com/) database and
bootstraps it if empty so no manual task there.

To start the API, install the Java Runtime Environment version 11.0 or greater
and run:

```
cd ./api
LOG_LEVEL=info \
  clojure -M:start-api
```

If no stack trace is shown, you can leave the process running and then:

```
yarn install
# Regenerate GraphQL domain classes and React Hooks:
yarn codegen
# Start the application in dev mode
yarn start
```

Visit:

- the `mobile` application in dev mode: http://localhost:3000/
- the GraphiQL UI: http://localhost:4000/graphiql
- the Voyager UI: http://localhost:4000/voyager

See the corresponding README files for detailed info about both sub-projects.

## Build and start

```
# Build the mobile app assets
cd ./packages/mobile
yarn build

# Copy these assets to the API resources folder
cd ../..
cp -r ./packages/mobile/build/* ./api/resources/mobile/

# Build the API
cd ./api
clojure -X:build

# Run the API that also serves the mobile app:
LOG_LEVEL=info java -jar cfapp-api.jar

# Visit http://localhost:3000/
```

## Authentication

Authentication of users is done through a third party OAuth provider:
[Auth0](https://auth0.com/).

### Normal flow of authentication

The authentication flow is as follows:

- if the mobile application detects that the user is not logged-in, it
  redirects her to the Auth0 login page
- there, she can create an account and/or login
- when performing any of these two, Auth0 uses REST endpoints from our API to
  create and/or validate the user credentials (see code snippets in
  `./api/auth0`)
- more actions are available to "admins" in the Auth0 UI
- communication between Auth0 and our API is secured by HTTP basic auth (hard
  coded id/password specific to each env)
- if authentication is successfull, Auth0 redirects the user back to the mobile
  app along with a JWT
- the mobile app will then detect a logged-in user and will thus grant access
  to the rest of the app
- when performing a GraphQL query, the mobile app adds the Auth0 JWT to the
  HTTP header
- when the API receives a GraphQL query, it checks
  - the JWT's signature was signed with the keys published by Auth0
  - the JWT _audience_ is equal to the ID of the Auth0 app of the environment
    (to prevent an attacker from using a token from one environment in another)
- if JWT is ok, the GraphQL query handling continues normally

### Local environment and Heroku review apps special case

When the application is run in a local environment or as a Heroku review app,
no Auth0 application is setup to call the corresponding API to check password
or create users because we cannot know it in advance.  In these cases, we use a
special Auth0 app that check user/password against a list of 4 hard coded users
(ID, email and password). These 4 users are also hard coded with the same ID,
email and passwords in empty databases (such as for review apps).

This allows us to have Auth0 deliver a valid JWT (which also contains the user
ID) to enable the rest of the authentication flow.

Nota: one can enable the full auth flow for a review app by configuring an
Auth0 app with
- the correct Auth0 snippets (effectively calling the correct API)
- the correct login/logout/CORS in Auth0 UI pointing the API

## Good to know

- If you need to install a dependency on a workspace, don't `cd` then `yarn
  install ${dep}` but run `yarn workspace ${workspace} add ${dep} -W`, this
  ensures said library is installed at the root rather than just the package.
  You might then need to `yarn install` at the root of the project.  Example
  adding a dev dependency: `yarn workspace @thecfapp/mobile add
  @graphql-codegen/cli -W -D`
- by default, `packages/mobile/package.json` field `homepage` is picked-up by
  `react-scripts` to determine a root path to serve the production application
  generated by `yarn build`. This is shown in relative paths used in the
  generated `index.html`. To prevent this, we specify `PUBLIC_URL=/` when
  building a production mobile app.
- At the root of the monorepo
  - file `system.properties` makes Heroku install the correct JVM version
  - file `app.json` declares `CLOJURE_CLI_VERSION` so that the Clojure Heroku
    build pack installs a recent version of Clojure. If missing, the default
    version of Clojure doesn't understand the parameters passed to `clj` or
    `clojure`.
  - file `project.clj` is there so that Heroku detects the project as being
    Clojure and install the Clojure build pack (which contains the Clojure
    binaries) but our project is not Leiningen, its deps.edn so `project.clj`
    is empty (build is overriden by `bin/build`).
  - file `bin/build` overrides the Clojure build pack behavior which expects
    the project to use Leiningen
  - file `package.json` is here only so that Heroku (to which we specified this
    project requires de Node.js build pack) doesn't fail. It looked painful to
    even try to make Heroku build a Node.js in a subfolder so we've kept the
    root `package.json` which declares `packages/mobile` as the sole workspace.
