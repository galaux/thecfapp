# CFApp

A CrossFit workout tracker. I wrote it to explore Clojure end to end: a GraphQL API over Datomic, a
ClojureScript re-frame front-end and Auth0 for authentication.

The part I find most interesting is the input format: workouts are typed as free text, the way one
writes them on a whiteboard, and an ANTLR grammar parses them into a structured model.

Nota: this repository is archived. I last worked on it in 2023 and I publish it as a work sample,
not as something to run. I started a React Native front-end on branches but never finished it, so
what is here is the web build.

## Parsing workouts

```
"Joe"
AMRAP 15'

for time
5 pull-ups
10 push-ups

1' rest
```

This parses into nested loops, each one with a header. Each exercise carries a rep count, a movement
and an application, which is the load, distance or duration attached to it.

Three parts make this work:

- `env/dev/resources/grammars/Workout.g4` handles the structure: workout names, `for time` with an
  optional round count or rep scheme (`1-2-3-4-…`), `AMRAP`, `EMOM` with a period, time caps, nested
  loops, and applications written as `@15kg`, `(15/12kg)`, `12kg/10Kg`, `1.25 BW` or `12"`
- `env/dev/resources/grammars/Movement.g4` holds the movement vocabulary. One doesn't edit it: it is
  generated by `env/dev/clj/cfapp/api/domain/movement/core.clj` from a taxonomy I wrote as Clojure
  data (`squat.clj`, `snatch.clj`, `kettlebell_swing.clj`, …), so adding a movement means editing
  Clojure, not a grammar
- `src/clj/cfapp/api/domain/parse/workout_visitor.clj` is the ANTLR visitor that lowers the parse
  tree into the domain model. It uses `movement.clj`, also generated, to map grammar tokens to
  `:movement.id/…` keywords

`bin/test-grammar.sh` is a shunit2 suite that exercises the grammar rule by rule, from
`(duration 1 minute)` up to a whole nested workout.

A natural language is ambiguous where a programming language isn't, so one can't always follow the
usual ANTLR advice. The header comment of `Workout.g4` goes through that trade-off: how much to
resolve in the lexer and how much to leave to the visitor.

I also published a smaller standalone version of the workout grammar, without the movement
vocabulary: [galaux/workout-grammar](https://github.com/galaux/workout-grammar).

## Repository organisation

This monorepo hosts two main parts. Its file hierarchy displays some peculiarities in order to meet
Heroku's Build Packs requirement:

```
.
├── deps.edn            Clojure API
├── shadow-cljs.edn     ClojureScript front-end
├── package.json        JS dependencies for the shadow-cljs build
├── src/
│   ├── clj/cfapp/api/      GraphQL API, Datomic, parsing, auth
│   ├── cljs/cfapp/mobile/  re-frame front-end
│   └── cljc/cfapp/common/  shared
├── env/                per-environment config, grammars, movement taxonomy
├── test/               Clojure and ClojureScript tests
├── spec/               front-end component specs
├── auth0/              Auth0 custom database scripts, real and fake
├── docs/
└── bin/                build and grammar test scripts
```

## How to use this repository

### Start the API

The API ships an in-memory [Datomic](https://www.datomic.com/) database and bootstraps it if empty
so no manual task there. One needs the Java Runtime Environment version 11.0 or greater, then:

```sh
LOG_LEVEL=info clojure -M:start-api
```

Then visit:

- the front-end in dev mode: <http://localhost:8080/>
- the GraphiQL UI: <http://localhost:4000/graphiql>
- the Voyager UI: <http://localhost:4000/voyager>

### Work on the front-end

```sh
npx shadow-cljs watch mobile
```

Then visit <http://localhost:8280/>. See [README.mobile.md](./README.mobile.md) for the rest: editor
setup, tests, shadow-cljs actions and debug logging.

### Work on the grammar

```sh
yarn compile-grammar
bin/test-grammar.sh
```

`compile-grammar` generates the parser into `./classes/workout`, which is where
`bin/test-grammar.sh` expects to find it.

## Build process

1. build the front-end
   - produces result in `./resources/public`
   - `yarn release`
2. build the API
   - serves the API along with the result produced by the previous step
   - `clojure -T:build uber`

Run the result with: `LOG_LEVEL=info java -jar ./target/cfapp.jar`

## Authentication

Authentication of users is done through a third party OAuth provider:
[Auth0](https://auth0.com/).

The authentication flow is as follows:

- if the front-end detects that the user is not logged-in, it redirects her to the Auth0 login page
- there, she can create an account and/or login
- when performing any of these two, Auth0 uses REST endpoints from our API to create and/or validate
  the user credentials (see code snippets in [`./auth0`](./auth0))
- communication between Auth0 and our API is secured by HTTP basic auth, with a shared id/password
  specific to each env
- if authentication is successfull, Auth0 redirects the user back to the app along with a JWT
- when performing a GraphQL query, the app adds the Auth0 JWT to the HTTP header
- when the API receives a GraphQL query, it checks
  - the JWT's signature was generated with the keys published by Auth0
  - the JWT _audience_ is equal to the ID of the Auth0 app of the environment, to prevent an
    attacker from using a token from one environment in another

### Local environment and Heroku review apps special case

When the application is run in a local environment or as a Heroku review app, no Auth0 application
can be setup to call the corresponding API because we cannot know its URL in advance. For these
cases, we use a special Auth0 app that checks user/password against a list of 4 hard coded users
(ID, email and password). These 4 users are also hard coded with the same ID, email and passwords in
empty databases, such as for review apps.

To know the credentials of these hard-coded users, see the [_fake_ Auth0 application
snippets](./auth0/fake/login.js).

This allows us to have Auth0 deliver a valid JWT, which also contains the user ID, to enable the
rest of the authentication flow.

## Heroku integration

To create a Heroku app, one needs to manually specify in the Heroku UI for the app:

- the list of build packs in this order:
  - Node.js
  - Clojure
- all environment variables (Heroku calls them _Config vars_) that are listed in `./app.json` as
  well as `HEROKU_APP_NAME`: the name of the Heroku application. We need to communicate this to the
  application as it is used by Heroku in the URL.

## Good to know

- the REPL doesn't seem to detect when one removes the DB files on disk – which one can do to
  reinitialize the DB along with the schema for instance. Subsequent restart of the application at
  the REPL will yield an exception `"datomic db not found"`. The only way out seems to be to restart
  a REPL.
