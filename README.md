## Repository organisation

This Git repository is a monorepo that hosts three main parts:
- a Clojure GraphQL API project at the root of the repo
- a Views React TypeScript in directory `./views`
- a ClojureScript Mobile application using project Views (see
  `./README.mobile.md` for more detail)

In order to meet Heroku's Build Packs requirement, this monorepo displays some
peculiarities in its file hierarchy:

```
.
├── docs/
│   └── deps.edn
├── views/
│   └── package.json
├── bin/
│   └── build
├── app.json
├── deps.edn
├── package.json
├── project.clj
├── README.md
├── pom.xml
├── Procfile
├── system.properties
└── yarn.lock
```

- `./views/package.json`: Yarn configuration for the Views project. Bundles
  React views in a JavaScript file used by project Mobile.
- `./package.json`: Mobile project Yarn configuration using the result of
  project Views to build a full React mobile application (with Shadow CLJS).
- `./shadow-cljs.edn`: Mobile project Shadow CLJS configuration using the
  result of project Views to build a full React mobile application.
- `./deps.edn`: Clojure project serving a GraphQL API and the static assets
  produced by project Mobile.
- `./project.clj`: an empty placeholder required by the Heroku Clojure Build
  Pack installation.
- `./bin/build`: a shell script overriding the Clojure Build Pack default
  behavior to use Leiningen.
- `./pom.xml`: an empty Maven placeholder required by the Heroku Java Build
  Pack (the Java Build Pack must be installed because Shadow CLJS requires
  `java` in the `PATH`).
- `./system.properties`: picked-up by Heroku to know the JVM version to
  install.
- `app.json`: Heroku slug configuration.
- `Procfile`: Heroku file to specify how to run the whole application.

## Build process

The (production) build process requires the tree following steps:

1. build project Views
   - generates `./src/js/views.js`
   - `yarn --cwd views build`
2. build project Mobile
   - uses `views.js` generated by the previous step
   - produces result in `./resources/public`
   - `yarn build` (also builds Views)
3. build project API
   - serves API along with result produced by the previous step
   - `npx shadow-cljs release mobile`

Run the result with: `LOG_LEVEL=info java -jar ./target/cfapp.jar`


## How to use this repository

### Work on the Views project

The Views project is a regular [Create React
App](https://github.com/facebook/create-react-app) project. The mains scripts
can be run when in the `./views` directory:

- `yarn start`
- `yarn storybook`

Remember: the started dummy application does not have the ability to talk to an
API.


### Work on the Mobile project

The Mobile project can be started with the following steps

1. check the Views project is bundled: `yarn --cwd views build`
2. `npx shadow-cljs watch mobile`
3. visit http://localhost:8280/

You may then want to start an API.


### Start the API (without serving the mobile app)

The API ships an in-memory [Datomic](https://www.datomic.com/) database and
bootstraps it if empty so no manual task there.

To start the API, install the Java Runtime Environment version 11.0 or greater
and run: `LOG_LEVEL=info clojure -M:start-api`. Then visit:

- the Mobile application in dev mode: http://localhost:8080/
- the GraphiQL UI: http://localhost:4000/graphiql
- the Voyager UI: http://localhost:4000/voyager


## Authentication

Authentication of users is done through a third party OAuth provider:
[Auth0](https://auth0.com/).


### Normal flow of authentication

The authentication flow is as follows:

- if the mobile application detects that the user is not logged-in, it
  redirects her to the Auth0 login page
- there, she can create an account and/or login
- when performing any of these two, Auth0 uses REST endpoints from our API to
  create and/or validate the user credentials (see code snippets in
  `./api/auth0`)
- more actions are available to "admins" in the Auth0 UI
- communication between Auth0 and our API is secured by HTTP basic auth (shared
  id/password specific to each env)
- if authentication is successfull, Auth0 redirects the user back to the mobile
  app along with a JWT
- the mobile app will then detect a logged-in user and will thus grant access
  to the rest of the app
- when performing a GraphQL query, the mobile app adds the Auth0 JWT to the
  HTTP header
- when the API receives a GraphQL query, it checks
  - the JWT's signature was generated with the keys published by Auth0
  - the JWT _audience_ is equal to the ID of the Auth0 app of the environment
    (to prevent an attacker from using a token from one environment in another)
- if JWT is ok, the GraphQL query handling continues normally


### Local environment and Heroku review apps special case

When the application is run in a local environment or as a Heroku review app,
no Auth0 application can be setup to call the corresponding API to check
password or create users because we cannot know it in advance. For these cases,
we use a special Auth0 app that checks user/password against a list of 4 hard
coded users (ID, email and password). These 4 users are also hard coded with
the same ID, email and passwords in empty databases (such as for review apps).

To know the credientials of these hard-coded users in a local environment or in
one of Heroku's review apps, see the [_fake_ Auth0 application
snippets](./api/auth0/fake/login.js).

This allows us to have Auth0 deliver a valid JWT (which also contains the user
ID) to enable the rest of the authentication flow.

Nota: one can enable the full auth flow for a review app by configuring an
Auth0 app with
- the correct Auth0 snippets (effectively calling the correct API)
- the correct login/logout/CORS in Auth0 UI pointing the API

## Good to know

- the REPL doesn't seem to detect when one removes the DB files on disk – which
  one can do to reinitialize the DB along with the schema for instance.
  Subsequent resart of the application at the REPL will yield an exception
  `"datomic db not found"`. The only way out seems to be to restart a REPL.
